# Expandable Segments 特性设计与实现文档

## 一、背景与动机

### 1.1 问题场景

在深度学习推理场景中，batch size 经常会动态变化。当程序以 batch size N 运行时，分配器会创建适合该大小的内存段。当 batch size 变为 N+1 时，需要分配略大的新段，而旧段中会留下无法复用的"碎片"（slivers）。

代码注释（[NPUCachingAllocator.cpp:318-341](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L318-L341)）描述了这一经典问题：

```text
传统模式下的内存布局（batch size 从 N 变为 N+1）：

段1: [A(N*A)    | 空闲sliver]   ← 空间不够放 (N+1)*A，但空闲部分无法被其他段复用
段2: [B(N*A*B)  | 空闲sliver]   ← 同理
段3: [C(N*C)    | 空闲sliver]   ← 同理
...
段50: [需要新malloc (N+1)*A*B]  ← 必须新分配，可能OOM

50+ 层的模型可能产生 50+ 个 slivers，大量内存被浪费。
```

### 1.2 解决思路

Expandable Segments 的核心思想：**不是每次分配创建一个独立段，而是为每个 stream 创建一个可增长的段，所有分配紧密排列在其中**。当需要更多空间时，在段末尾追加物理内存页。

```
Expandable 模式下的内存布局：

段1: [A | B | C | ... | 空闲虚拟地址空间(未映射物理内存)]
                                    ↑ 需要时再映射物理页

当 batch size 从 N 变为 N+1：
段1: [A' | B' | C' | ... | 新映射的物理页]
     ↑原地扩展，无需新段，无 slivers
```

### 2.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **虚拟/物理分离** | 虚拟地址空间一次性预留（可达 NPU 总内存 1.125 倍），物理内存按需映射 |
| **页粒度管理** | 小池 2MB 页、大池 20MB 页，1G 页模式使用 1GB 页 |
| **最低地址优先** | 分配时从最低地址搜索，鼓励分割块合并，减少碎片 |
| **物理句柄缓存** | unmap 时缓存物理句柄而非释放，map 时优先复用，减少系统调用开销 |
| **可动态开关** | 运行期间可切换 expandable_segments，禁用后不再向可扩展段分配 |

## 四、核心数据结构

### 4.1 ExpandableSegment

代码位置：[NPUCachingAllocator.cpp:394-689](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L394-L689)

```cpp
struct ExpandableSegment {
    int device_;                                    // NPU 设备号
    std::optional<aclrtStream> stream_;             // 关联的 stream
    void *ptr_{};                                   // 虚拟地址空间起始地址
    size_t max_handles_;                            // 虚拟地址空间可容纳的最大页数
    size_t segment_size_;                           // 每页大小 (2MB/20MB/1GB)

    struct Handle {
        aclrtDrvMemHandle handle;                   // 物理内存句柄
        std::optional<uint64_t> shareableHandle;    // IPC 共享句柄
    };
    std::vector<std::optional<Handle>> handles_;    // 页表：每页对应一个物理句柄
    std::shared_ptr<c10d_npu::HCCLComm> hcclComm_;  // HCCL 通信句柄
};
```

**内存布局示意**：

```
虚拟地址空间:  [page0] [page1] [page2] [page3] [page4] ... [pageN]
               ←─────────────── max_handles_ × segment_size_ ──────────→

handles_:      [H1]    [nullopt] [H2]   [H3]    [nullopt] ...
               已映射    未映射    已映射   已映射    未映射

物理内存:      [2MB]              [2MB]   [2MB]
```

### 4.2 Block（扩展字段）

#### 5.1.2 查找可扩展块：find_expandable_block

代码位置：[NPUCachingAllocator.cpp:2227-2283](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2227-L2283)

```
find_expandable_block(device, stream, pool, size)
    │
    ├── 1. 在 pool->unmapped 中按地址从低到高搜索
    │   │   对每个 unmapped 块：
    │   │   ├── 检查前一个块是否也可用（空闲且已映射）
    │   │   ├── 从该位置向后遍历，累计可用地址空间
    │   │   └── 如果累计空间 >= size，返回该候选块
    │   │
    │   └── lambda: has_available_address_space
    │       沿 next 指针遍历，累计连续可分配（空闲+无事件+无流使用）块的大小
    │
    ├── 2. 如果没有找到合适的空间
    │   │   创建新的 ExpandableSegment
    │   │   ├── 页大小: 小池 2MB, 大池 20MB (可配置), 1G模式 1GB
    │   │   ├── AclrtReserveMemAddress 预留虚拟地址空间
    │   │   └── 创建 Block(mapped=false) 插入 pool->unmapped
    │   │
    │   └── 返回新创建的候选块
    │
    └── 返回候选块
```

核心搜索逻辑：

```cpp
auto allocatable = [](Block *b) {
    return b && !b->allocated && b->event_count == 0 && b->stream_uses.empty();
};

auto has_available_address_space = [&](Block *b) {
    size_t bytes = 0;
    while (bytes < size && allocatable(b)) {
        bytes += b->size;
        b = b->next;
    }
    return bytes >= size;
};

for (auto it = pool->unmapped.lower_bound(&key);
     it != pool->unmapped.end() && (*it)->stream == stream; ++it) {
    Block *c = *it;
    if (allocatable(c->prev)) {
        c = c->prev;  // 尝试从前一个已映射空闲块开始
    }
    if (has_available_address_space(c)) {
        return c;
    }
}
```

#### 5.1.3 映射物理内存：map_block

代码位置：[NPUCachingAllocator.cpp:2285-2331](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2285-L2331)

```
map_block(to_map, size, ctx, map_pool)
    │
    ├── 1. 调用 ExpandableSegment::map() 映射物理内存
    │   └── 如果返回 size==0，表示 OOM，返回 false
    │
    ├── 2. 从 pool->unmapped 中移除 to_map
    │   设置 to_map->mapped = true
    │
    ├── 3. 如果映射范围 < to_map->size（映射了部分页）
    │   ├── 创建 remaining Block（未映射部分）
    │   ├── remaining->mapped = false
    │   ├── remaining->expandable_segment_ = to_map->expandable_segment_
    │   ├── 插入链表：to_map → remaining → to_map->next
    │   └── pool->unmapped.insert(remaining)
    │
    ├── 4. try_merge_blocks(to_map, to_map->prev, pool)
    │   try_merge_blocks(to_map, to_map->next, pool)
    │   └── 合并相邻的同状态（mapped/unmapped）块
    │
    ├── 5. pool->blocks.insert(to_map)
    │
    └── 6. 更新统计信息，记录 TraceEntry::SEGMENT_MAP
```

#### 5.1.4 ExpandableSegment::map（底层映射）

代码位置：[NPUCachingAllocator.cpp:435-484](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L435-L484)

```
ExpandableSegment::map(range, pool)
    │
    ├── 1. 计算需要映射的页范围 [begin, end)
    │   begin = segmentLeft(range.ptr)   → 向下取整到页边界
    │   end   = segmentRight(range.ptr + range.size) → 向上取整到页边界
    │
    ├── 2. 扩展 handles_ 向量（如果需要）
    │
    ├── 3. 为每个页分配物理内存
    │   for i in [begin, end):
    │   ├── 优先从 pool->free_physical_handles_ 复用
    │   │   └── 取出最后一个缓存句柄，跳过 AclrtMallocPhysical
    │   │
    │   └── 否则调用 AclrtMallocPhysical 分配新物理页
    │       └── OOM 时回滚：释放已分配的所有 handle，返回 size=0
    │
    ├── 4. 将物理内存映射到虚拟地址
    │   for i in [begin, end):
    │       AclrtMapMem(ptr_ + i*segment_size_, segment_size_, handles_[i].handle)
    │
    └── 5. 返回实际映射的范围 rangeFromHandles(begin, end)
```

**关键设计**：物理内存分配和映射分两步完成。先分配所有页的物理内存，再统一映射。如果中途 OOM，可以干净地回滚。

#### 5.1.5 组合分配：try_allocate_expandable_block

代码位置：[NPUCachingAllocator.cpp:2333-2363](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2333-L2363)

```
try_allocate_expandable_block(device, stream, pool, size, ctx)
    │
    ├── 1. find_expandable_block() → candidate
    │
    ├── 2. 如果 candidate 未映射，先 map_block(candidate, min(candidate.size, size))
    │
    ├── 3. while candidate->size < size:
    │   │   需要更多空间，继续映射 candidate->next
    │   │   ├── remaining = size - candidate->size
    │   │   ├── new_candidate = candidate->next
    │   │   └── map_block(new_candidate, min(remaining, new_candidate->size))
    │   │       → map_block 内部会 try_merge_blocks，合并 candidate 和 new_candidate
    │   └── candidate = new_candidate
    │
    └── 4. pool->blocks.erase(candidate)，返回 candidate
```

**典型场景**：

```
初始状态：
  [mapped_free 10MB] → [unmapped 50MB] → null

请求 30MB：
  1. candidate = mapped_free (10MB)
  2. candidate->size(10MB) < 30MB，进入循环
  3. map_block(unmapped, 20MB)
     → 映射 20MB 物理内存
     → 剩余 30MB 仍为 unmapped
     → try_merge_blocks 合并 mapped_free 和新映射的 20MB
  4. 现在 candidate->size = 30MB >= 30MB，退出循环
  5. 从 blocks 中移除，返回给调用者
```

### 5.2 内存释放流程

#### 5.2.1 free_block 中的特殊处理

代码位置：[NPUCachingAllocator.cpp:2361-2422](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2361-L2422)

#### 5.2.2 unmap_block：解除物理内存映射

代码位置：[NPUCachingAllocator.cpp:2874-2930](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2874-L2930)

```
unmap_block(block, context, free_physical)
    │
    ├── 1. ExpandableSegment::unmap(range, pool)
    │   │   计算完全空闲的页范围 [begin, end)
    │   │   调用 unmapHandles(begin, end, pool)
    │   │
    │   └── unmapHandles:
    │       ├── npuSynchronizeDevice()  ← 确保所有 NPU 操作完成
    │       ├── for each page:
    │       │   ├── AclrtUnmapMem()     ← 解除虚拟地址映射
    │       │   └── if pool:
    │       │       pool->free_physical_handles_.push_back(handle)  ← 缓存句柄
    │       │     else:
    │       │       AclrtFreePhysical(handle)  ← 直接释放物理内存
    │       └── trimHandles()  ← 清理 handles_ 尾部的 nullopt
    │
    ├── 2. 从 pool->blocks 中移除 block
    │
    ├── 3. 处理 unmap 范围前后的剩余已映射部分
    │   ├── before_size > 0 → 创建 before_free (mapped=true)
    │   └── after_size  > 0 → 创建 after_free  (mapped=true)
    │
    ├── 4. 更新 block 为 unmapped 状态
    │   block->mapped = false
    │
    ├── 5. try_merge_blocks(block, block->prev)  ← 合并相邻 unmapped 块
    │   try_merge_blocks(block, block->next)
    │
    ├── 6. pool->unmapped.insert(block)
    │
    └── 7. 更新统计信息，记录 TraceEntry::SEGMENT_UNMAP
```

**unmap 的对齐约束**（[NPUCachingAllocator.cpp:489-497](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L489-L497)）：

```cpp
SegmentRange unmap(SegmentRange range, BlockPool *pool) {
    auto begin = segmentRight(range.ptr);       // 向上取整到页边界
    auto end = segmentLeft(range.ptr + range.size);  // 向下取整到页边界
    if (begin >= end) {
```

只有完全空闲的页（不与活跃分配共享页边界）才能被 unmap。

### 5.3 OOM 处理流程

代码位置：[NPUCachingAllocator.cpp:1250-1264](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L1250-L1264)

```
alloc_block 失败（OOM）
    │
    ├── npuSynchronizeDevice(true)  ← 确保所有异步操作完成
    │
    ├── release_cached_blocks(true, context, true)
    │   │   free_physical = true 意味着：
    │   │   ├── unmap 时直接 AclrtFreePhysical（不缓存句柄）
    │   │   └── 释放 pool 中所有 free_physical_handles_
    │   │
```

**关键**：OOM 时 `free_physical=true`，物理内存被真正释放回系统，而非缓存。这是可扩展段相比传统模式的优势——传统模式只能释放完整的空闲段，而可扩展模式可以按页释放。

```cpp
     it != pool->unmapped.end() && (*it)->stream == stream; ++it) {
```

**效果**：当 OOM 导致中间出现 unmapped 空洞后，新分配会优先填充这些空洞，使分割的块重新合并。

### 6.2 Best-Fit 搜索中的可扩展大小

代码位置：[NPUCachingAllocator.cpp:2539-2554](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2539-L2554)

在 `get_free_block` 中搜索最佳匹配时，可扩展块的实际可用大小需要考虑其后方的未映射空间：

```cpp

    return b->size + (b->next && !b->next->mapped ? b->next->size : 0);
};
```

这使得分配器在选择块时，会考虑块的可扩展潜力，而不仅仅是当前已映射的大小。

### 6.3 should_split 策略差异

代码位置：[NPUCachingAllocator.cpp:2489-2497](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L2489-L2497)

```cpp
bool should_split(const Block *block, size_t size) {
    size_t remaining = block->size - size;
    if (block->pool->is_small || CachingAllocatorConfig::expandable_segments()) {
        return remaining >= kMinBlockSize;  // 512B
    } else {
        return (size < max_split_size()) && (remaining > kSmallSize);  // 1MB
    }
}
```

可扩展模式下分割更积极（阈值 512B vs 1MB），因为：
- 分割出的小块仍在同一个虚拟地址段内
- 空闲页可以随时 unmap 回收
- 不会产生传统意义上的"死碎片"

### 6.4 物理句柄缓存机制

```
map 时：
  ┌─────────────────────────────────┐
  │ free_physical_handles_ 非空？   │
  │   ├── YES → 取出最后一个句柄复用 │  ← 无需 AclrtMallocPhysical
  │   └── NO  → AclrtMallocPhysical │  ← 分配新物理页
  └─────────────────────────────────┘

unmap 时：
  ┌─────────────────────────────────────┐
  │ free_physical 参数？                 │
  │   ├── true  → AclrtFreePhysical     │  ← 真正释放物理内存
  │   └── false → push_back 到缓存      │  ← 保留供后续复用
  └─────────────────────────────────────┘
```

| 场景 | free_physical | 效果 |
-----|--------------|------|
| OOM 重试 | true | 物理内存真正释放回系统 |
| emptyCache | true | 完全清理，释放所有物理内存 |
| emptyVirtAddrCache | false | 仅释放虚拟地址映射，物理句柄缓存 |
| 日常 unmap_block | false | 缓存句柄，加速后续 map |

## 八、辅助工具函数

代码位置：[NPUCachingAllocat.cpp:644-664](file:///home/cjj/torch_npu/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp#L644-L664)

```cpp
// 计算包含 size 字节需要的页数（向上取整）
size_t numSegments(size_t size) { return (size + segment_size_ - 1) / segment_size_; }

// 给定地址 p，计算其所在页的索引（向下取整）
size_t segmentLeft(char *p) { return static_cast<size_t>(p - ptr()) / segment_size_; }

// 给定地址 p，计算其后的页索引（向上取整）
size_t segmentRight(char *p) { return numSegments(p - ptr()); }

// 根据页索引范围构造 SegmentRange
SegmentRange rangeFromHandles(size_t begin, size_t end) {
    return SegmentRange(ptr() + segment_size_ * begin, segment_size_ * (end - begin));
}
```

**对齐示意**：

```
segment_size_ = 20MB

地址:    0MB       20MB       40MB       60MB       80MB
         |----------|----------|----------|----------|
页索引:     0          1          2          3

segmentLeft(25MB)  = 1  (25/20 = 1.25 → 1)
segmentRight(25MB) = 2  (ceil(25)
segmentLeft(40MB)  = 2
segmentRight(40MB) = 2

map(SegmentRange{20MB, 30MB}):
  begin = segmentLeft(20MB)  = 1
  end   = segmentRight(50MB) = 3
  → 映射页 1 和页 2，实际映射 40MB (20MB~60MB)
```

## 十三、与传统模式的对比总结

| 维度 | 传统模式 (`expandable_segments=False`) | 可扩展模式 (`expandable_segments=True`) |
|------|---------------------------------------|----------------------------------------建** | `AclrtMallocAlign32` 一次性分配物理内存 | `AclrtReserveMemAddress` 预留虚拟地址，按需映射物理页 |
| **段大小** | 固定，由 `get_allocation_size` 决定 | 动态增长，虚拟地址空间可达 NPU 总内存 1.125 倍 |
| **分配粒度** | 整段分配 | 按页映射（2MB/20MB/1GB） |
| **空闲回收** | 只能释放完整空闲段 | 可按页 unmap 回收物理内存 |
| **碎片类型** | 段间碎片（slivers） | 页内对齐碎片（较小） |
| **OOM 恢复**闲段，可能无法回收足够空间 | 按页释放空闲物理内存，回收更灵活 |
| **分割策略** | `remaining > kSmallSize(1MB)` | `remaining >= kMinBlockSize(512B)` |
| **inactive_split** | 计入统计 | 不计入（空闲页总是可释放的） |
| **初始分配速度** | 快（单次 `AclrtMallocAlign32`） | 稍慢（需 `AclrtMallocPhysical` + `AclrtMapMem`） |
| **IPC 支持** | 支持 | 不支持（可临时禁用） |
| **配置互斥** | 无 | 与 `max_split_size_mb`、`garbage_collection_threshold` 互斥 |
| **底层 API** | `AclrtMallocAlign32` / `AclrtFree` | `AclrtReserveMemAddress` / `AclrtMallocPhysical` / `AclrtMapMem` / `AclrtUnmapMem` / `AclrtFreePhysical` / `AclrtReleaseMemAddress` |

## 十四、已知限制

1. **初始分配速度较慢**：每次 map 需要调用 `AclrtMallocPhysical` + `AclrtMapMem`，比单次 `AclrtMallocAlign32` 慢
2. **IPC 不支持**：可扩展段的 NPU 张量不能跨进程共享（如多进程 DataLoader），但可临时禁用 `expants` 来分配需要跨进程的张量
3. **物理内存句柄不可拆分**：NPU API 限制，一个物理句柄映射后不能拆分，即使它包含多个页
4. **map/unmap 开销与句柄数成正比**：映射 10 个独立的 2MB 页比映射 1 个 20MB 页慢 10 倍
5. **unmap 需要同步**：`unmapHandles` 中调用 `npuSynchronizeDevice()`，这是一个昂贵的同步操作
6. **与 NPU Graph 的兼容性**：`pin_memory_expandable_segments` 与 ACLGraph capture 不兼容
