Expandable Segments 特性设计与实现文档

一、背景与动机

1.1 问题场景

在深度学习推理场景中，batch size 经常会动态变化。当程序以 batch size N 运行时，分配器会创建适合该大小的内存段。当 batch size 变为 N+1 时，需要分配略大的新段，而旧段中会留下无法复用的”碎片”（slivers）。

代码注释（NPUCachingAllocator.cpp:318-341）描述了这一经典问题：

1.2 解决思路

Expandable Segments 的核心思想：不是每次分配创建一个独立段，而是为每个 stream 创建一个可增长的段，所有分配紧密排列在其中。当需要更多空间时，在段末尾追加物理内存页。

二、整体架构

2.1 架构图

2.2 核心设计原则

原则 说明
虚拟/物理分离 虚拟地址空间一次性预留（可达 NPU 总内存 1.125 倍），物理内存按需映射
页粒度管理 小池 2MB 页、大池 20MB 页，1G 页模式使用 1GB 页
最低地址优先 分配时从最低地址搜索，鼓励分割块合并，减少碎片
物理句柄缓存 unmap 时缓存物理句柄而非释放，map 时优先复用，减少系统调用开销
可动态开关 运行期间可切换 expandable_segments，禁用后不再向可扩展段分配

4.2 Block（扩展字段）

代码位置：NPUCachingAllocator.cpp:231-309

与 expandable_segments 相关的两个关键字段：

  • mapped = true：块有物理内存支撑，可正常使用
  • mapped = false：块仅占虚拟地址空间，无物理内存，存在于 pool->unmapped 集合中
  • expandable_segment_ = nullptr：传统模式分配的块，mapped 始终为 true

4.3 BlockPool（扩展字段）

代码位置：NPUCachingAllocator.cpp:213-227

  • blocks：存放 mapped=true 的空闲块，按大小排序，用于 best-fit 分配
  • unmapped：存放 mapped=false 的虚拟地址块，按地址排序，用于最低地址优先分配
  • free_physical_handles_：unmap 时缓存的物理句柄，map 时优先复用

六、关键策略详解

6.1 最低地址优先分配

在 find_expandable_block 中，pool->unmapped 按地址排序，搜索从 lower_bound 开始，即从最低地址开始查找。

效果：当 OOM 导致中间出现 unmapped 空洞后，新分配会优先填充这些空洞，使分割的块重新合并。

6.2 Best-Fit 搜索中的可扩展大小

代码位置：NPUCachingAllocator.cpp:2539-2554

在 get_free_block 中搜索最佳匹配时，可扩展块的实际可用大小需要考虑其后方的未映射空间：

这使得分配器在选择块时，会考虑块的可扩展潜力，而不仅仅是当前已映射的大小。

6.3 should_split 策略差异

代码位置：NPUCachingAllocator.cpp:2489-2497

可扩展模式下分割更积极（阈值 512B vs 1MB），因为：

  • 分割出的小块仍在同一个虚拟地址段内
  • 空闲页可以随时 unmap 回收
  • 不会产生传统意义上的”死碎片”

6.4 物理句柄缓存机制

场景 free_physical 效果
OOM 重试 true 物理内存真正释放回系统
emptyCache true 完全清理，释放所有物理内存
emptyVirtAddrCache false 仅释放虚拟地址映射，物理句柄缓存
日常 unmap_block false 缓存句柄，加速后续 map

6.5 try_merge_blocks 的映射状态约束

代码位置：NPUCachingAllocator.cpp:2424-2430

只有 mapped 状态相同的相邻块才能合并。这确保了：

  • 已映射的空闲块之间可以合并
  • 未映射的虚拟地址块之间可以合并
  • 已映射和未映射的块不会错误合并

for (auto i : c10::irange(handles_.size())) {
if (handles_.at(i) && (i == 0 || !handles_.at(i - 1))) {

}
if (handles_.at(i) && (i + 1 == handles_.size() || !handles_.at(i + 1))) {
fn(start, i + 1); // 连续已映射区间的终点
}
}

十三、与传统模式的对比总结

| 维度 | 传统模式 (expandable_segments=False) | 可扩展模式 (expandable_segments=True) |
|——|—————————————|—————————————-建** | AclrtMallocAlign32 一次性分配物理内存 | AclrtReserveMemAddress 预留虚拟地址，按需映射物理页 |
| 段大小 | 固定，由 get_allocation_size 决定 | 动态增长，虚拟地址空间可达 NPU 总内存 1.125 倍 |
| 分配粒度 | 整段分配 | 按页映射（2MB/20MB/1GB） |
| 空闲回收 | 只能释放完整空闲段 | 可按页 unmap 回收物理内存 |
| 碎片类型 | 段间碎片（slivers） | 页内对齐碎片（较小） |
| OOM 恢复闲段，可能无法回收足够空间 | 按页释放空闲物理内存，回收更灵活 |
| 分割策略 | remaining > kSmallSize(1MB) | remaining >= kMinBlockSize(512B) |
| inactive_split | 计入统计 | 不计入（空闲页总是可释放的） |
| 初始分配速度 | 快（单次 AclrtMallocAlign32） | 稍慢（需 AclrtMallocPhysical + AclrtMapMem） |
| IPC 支持 | 支持 | 不支持（可临时禁用） |
| 配置互斥 | 无 | 与 max_split_size_mb、garbage_collection_threshold 互斥 |
| 底层 API | AclrtMallocAlign32 / AclrtFree | AclrtReserveMemAddress / AclrtMallocPhysical / AclrtMapMem / AclrtUnmapMem / AclrtFreePhysical / AclrtReleaseMemAddress |

十四、已知限制

  1. 初始分配速度较慢：每次 map 需要调用 AclrtMallocPhysical + AclrtMapMem，比单次 AclrtMallocAlign32 慢
  2. IPC 不支持：可扩展段的 NPU 张量不能跨进程共享（如多进程 DataLoader），但可临时禁用 expants 来分配需要跨进程的张量
  3. 物理内存句柄不可拆分：NPU API 限制，一个物理句柄映射后不能拆分，即使它包含多个页
  4. map/unmap 开销与句柄数成正比：映射 10 个独立的 2MB 页比映射 1 个 20MB 页慢 10 倍
  5. unmap 需要同步：unmapHandles 中调用 npuSynchronizeDevice()，这是一个昂贵的同步操作
  6. 与 NPU Graph 的兼容性：pin_memory_expandable_segments 与 ACLGraph capture 不兼容
